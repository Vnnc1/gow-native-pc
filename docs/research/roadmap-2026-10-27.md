## Public hardware target: stable 60 fps across supported tiers

The user's target is a public build that sustains 60 guest frames/s on modest machines as well as powerful PCs.
Treat the current laptop and the earlier RX 580 desktop as explicit optimization targets, not interchangeable
benchmarks. A stronger machine passing does not close a weaker machine's performance gate. Minimum requirements
must be established by measurements; this target is not a claim that every PC can already reach 60 fps.

| Validation tier | Reference / current evidence | Required follow-up |
|---|---|---|
| Modest laptop | i5-8265U, 24 GB, UHD 620 selected; 42.90 mean FPS in the prepared ship test at fixed 1x, audio off | Open 60 fps target; profile EE/VU1/GS and serial waits, then repeat with audio and visible presentation; record thermals/clocks and the selected GPU |
| Older discrete desktop | Xeon E5-2666 v3 + RX 580; historical measurements only | Run the current revision with the same test protocol; verify AMD rendering and heavy combat before claiming a stable 60 |
| Powerful desktop | No current result | Add contemporary CPU/GPU coverage, including NVIDIA; verify correct 60 Hz simulation, pacing and higher-resolution headroom |

Implementation order and release criteria:

1. Reduce common engine costs first: memory/call overhead, VU1 coverage, scheduling and synchronization, allocations
   and redundant graphics work, selected by measured frame-time contribution. Lower resolution is an option for a
   measured GPU bottleneck; it is not evidence that an EE/VU1 bottleneck has been fixed. Preserve memory, timing,
   rendering and audio correctness on every fast path.
2. Make presentation scalable through explicit quality settings and, after validation, bounded dynamic resolution.
   Document each tier's tested resolution/settings and keep manual overrides. Use extra capacity for image quality
   while retaining the intended simulation rate. Automatic tier/GPU selection remains work to validate, not shipped
   functionality. Never silently change Windows power settings or driver configuration.
3. Collect guest-frame intervals and actual presentation intervals, p95/p99, worst stalls and time over the 16.67 ms
   frame budget. Five-second FPS averages cannot certify a lock. Separate first-visit JIT/cache behavior from warmed
   gameplay; validate ship, heavy combat, new areas, transitions, FMVs, menus, saves and a sustained session of at
   least 30 minutes to expose thermal throttling and memory growth. Repeat controlled comparisons at least three
   times on each available tier, and report missing coverage explicitly.
4. Require visible-window runs with sound enabled before declaring a tier ready: no reproducible rendering errors,
   crashes, simulation drift or audio underruns attributable to the change. Audio correctness belongs to this gate;
   the later audio phase covers additional work, not permission to ship broken sound. Record interval distributions
   and remaining drops instead of accepting an average near 60 as "locked 60".
5. Keep installation viable on smaller machines: measure peak RAM, disk space, compile/link time and responsiveness;
   tune build concurrency and unity batches against memory pressure, with a user override. Separate first download,
   first compilation and incremental updates. Cached rebuild performance must not conceal an impractical first build.
6. Keep portable CPU/driver requirements explicit. CPU-specific optimizations need capability checks and a tested
   fallback; no distributing a machine-specific binary as the generic release. Accept community test reports with
   revision, CPU, selected GPU/driver, RAM, power mode, settings, scene and cache state, without bundling game data.

The current laptop has not met this 60 fps gate. The next runtime optimization must state which measured bottleneck
it addresses and compare before/after on the same hardware; the RX 580 and powerful-PC gates remain independent.

## 0. Where the frame time goes (baseline to beat)

Session observability (29c + launcher): bounded guest interval windows and CPU/memory/I/O samples, opt-in detailed
audio/VU1/IOP timing, player markers and reviewed local report ZIPs now support community reproduction. See
[reporting bugs](../reporting-bugs.md). Remaining instrumentation gates include actual presentation intervals,
GPU/VRAM sensors, controlled collection-overhead measurements and community coverage across the hardware tiers.
Diagnostic infrastructure itself is not an FPS improvement.

- Machine A (Xeon E5-2666 v3 + RX 580, clang + PGO): 58-60 fps on the ship, 55 in heavy areas.
- Critical path: the VU1 worker job (~13-14 ms) + a serial EE gap of ~3.5 ms between FINISH and the next frame's VIF
  kick. 16.67 ms is the budget: the gap is the margin between 55 and 60.
- VU1: JIT (patch 27) and AOT now run at ~0.99× the same instruction count; `VU1NativeAccess::chain` is ~130
  instructions per block, about half the cost of a typical block, shared by both.
- clang's VU1 code is 8-15 % slower than MSVC's; MSVC LTCG takes > 2.5 h, so clang + PGO is the shipped build.
- Measure everything with the same tools: `GOW_PERF=1` (per-frame EE / VU1 / GS split), `[diagnostics] frame_pc`
  (guest frames, `vid::Flip` 0x1837B8) vs host presents, `tools/test/vu1-ir-measure.sh` (instruction counts; wall
  time in the VM is noise).

## Phase 1: build and recompilation quality (top priority)

### 1.1 Patch 28 `recomp-direct-jal`: direct calls for static JAL (biggest codegen lever)

**Status: done (engine/patches/28-recomp-direct-jal.patch), in a safer form than the plan below.** The generated code
calls `runtime->callGuestFunction(rdram, ctx, TARGET, SRC, FALLTHROUGH)` (`ps2_runtime.h`, inline). It reads the same
function-table entry as the dispatcher (so overrides registered at run time with `replaceFunction` still apply; a
direct `fn_TARGET(...)` call would bypass them), charges the same 8-cycle checkpoint and keeps the same return checks
(stop request, pc 0, a callee that left pc at its entry, the jump serial now `g_ps2GuestJumpSerial` in the header).
It drops the per-call trace ring write, dispatch history push, `ps2_perf::guestEntry` and the trace `getenv` statics.
Escape hatches: `GOW_DISPATCH_FULL=1` or `PS2X_GS_WORKER_TRACE` (all calls take the full dispatch), calls to
`GOW_PERF_FRAME_PC` (so GOW_PERF still counts guest frames), missing targets (missing-function policy), and
`PS2X_STATIC_CALLS=dispatch` in the recompiler's environment (old code). clang -O2 does not inline it at each call site
(one shared out-of-line copy, ~60 instructions, direct TLS access, no wrapper), so code size does not grow.
Measured: micro-benchmark with an empty callee, Linux clang -O2, min of 6 runs: 9.5 → 6.3 ns per call. Parity test
`callGuestFunction matches dispatchGuestBranch DirectCall` (implicit return, transfer, checkpoint, tail jump to entry,
missing target). The Windows follow-up below now measures same-binary lean/full guest FPS. Next step for more:
let PGO inline it at hot sites, then a direct `fn_TARGET` call guarded by `table[slot] == fn_TARGET`.

Windows review (2026-10-28): call/return, checkpoint, override and codegen regressions pass; patch 29a fixes diagnostic
settings initialized before standalone boot restored its environment. With the supplied PT-BR disc, gameplay and
2,000 VU1 parity checks pass. Three paired ship runs on the i5-8265U/UHD 620 average 42.90 lean / 41.59 full guest FPS
(+3.2% observed, with run-to-run variation); this is not a main-branch comparison or general performance guarantee.
Frame-exact equivalence, later areas and other GPUs remain open gates. See [hardware evidence](../tested-hardware.md)
and [review and reproduction](patches-28-29-review.md).

Original plan:

What the code does today (`ps2xRecomp/src/lib/control_flow_emitter.cpp`, `ps2xRuntime/src/lib/ps2_runtime.cpp`
`dispatchGuestBranch`, ~line 1525):

- `emitDirectFunctionJumpIfAvailable` only handles `StaticBranchKind::Jump`. Every `JAL` to a known function is
  emitted as `runtime->dispatchGuestBranch(rdram, ctx, 0xTARGET, src, ret, DirectCall, "JAL")`.
- Per call, `dispatchGuestBranch` writes the `g_gowRing` trace ring, charges `eeCheckpointDue(kGuestDispatchCycles)`,
  looks up the function table, pushes the dispatch PC, calls `ps2_perf::guestEntry`, tests getenv-static trace flags,
  calls the target, then compares serials/PC on return.

Change:

- In the recompiler, when the JAL target is a function the same build defines (the function map knows it) and it
  has no runtime override, emit:
  `SET_GPR_U32(ctx, 31, ret); if (runtime->eeCheckpointDue(kGuestDispatchCycles)) { ctx->pc = TARGET; return; }`
  `fn_TARGET(rdram, ctx, runtime); if (ctx->pc != ret) return;`
- Keep `dispatchGuestBranch` for targets that are overridden (`game_overrides.cpp`, `src/gow_overrides.cpp`), for
  targets outside the map, and when a trace or perf env var is set at build time (a recompiler switch, e.g.
  `--direct-calls=off`, for debug builds).
- With codegen locals (patch 08, `ps2_cg.h`), flush the cached GPRs before the call and reload after it, exactly as
  the dispatch path does today; reuse the same helper.

Risks:

- An override registered at run time for a function the build calls directly would be bypassed. Fix: the recompiler
  reads the override list (`[runtime] overrides` + the runtime's registry dump) and never emits a direct call to an
  overridden address. Add a run-time assertion in debug builds: `dispatchGuestBranch` logs if an overridden target
  was reached without it.
- Host stack depth grows (direct recursion instead of the dispatcher's frame). The dispatcher already recurses, so
  the depth is the same order; check on the deepest recursion seen in-game (load screens).
- `pushDispatchPc` feeds crash reports; losing it on direct calls makes crash stacks shorter. Accept, or keep a
  cheap inline `push` behind a macro that release builds compile out.

Measure: `GOW_PERF=1` EE ms per frame on the ship and in A01MP02; a callgrind count of one guest frame
(`tools/test/vu1-ir-measure.sh`-style, with the EE runner instead of the VU1 bench). Expect a clear EE gain, because
JAL is the most common control transfer in the game.

Done when: the pad-script run (`[optimize]`) completes, frame hashes match a pre-patch run for the first N frames
(GS dump digest), and EE ms per frame drops.

### 1.2 Patch 29 `recomp-dispatch-trim`: cheaper dispatch for the calls that stay dynamic

**Status: done (engine/patches/29-recomp-dispatch-trim.patch).**

- `JALR` now calls `callGuestFunction(..., GuestBranchKind::IndirectCall, "JALR")`, the patch 28 lean path with a
  run-time target. No inline cache was needed: the lean path's table lookup is a subtract, a shift, one compare and one
  load, which is what a cache hit would cost. A target outside the table, misaligned or missing takes the full dispatch,
  which reports it with kind IndirectCall / "JALR" as before. `PS2X_STATIC_CALLS=dispatch` covers JALR too.
- `JR rX` to an external target (IndirectJump) stays on `dispatchGuestBranch`: a jump always returns to the central
  dispatcher loop, so the dispatch is not on a hot per-call path.
- In `dispatchGuestBranch`, the PS2X_GS_WORKER_TRACE statics moved into helpers behind `g_ps2FullCallDispatch`
  (which that variable sets), so a normal call no longer touches their guards. The branch ring stays: after patch 28
  only jumps, missing targets and diagnostic runs reach it, and it feeds the "main thread dormant" dump.
- `ps2TraceGuestWrite` is deleted: from the write macros, from `PS2Runtime::Store8..128` (the 128-bit one also copied
  the value to the stack for it) and from the recompiler's constant-address writes (`genFastWrite`). It was an empty
  inline function, so the optimised code does not change except `Store128`; the gain is less generated source and
  less front-end work per store. `ps2TraceGuestRangeWrite` (also empty) is left: its callers are stubs, not hot code.
- Test: the parity test runs every case for both DirectCall/JAL and IndirectCall/JALR.

Follow-up 29a restores the trace interval's original start (first dispatched call, including an unwatched one).
Follow-up 29b repairs two stale MMIO assertions in the existing codegen suite, now 68/68 passing on Windows.
The dedicated call suite passes all ten isolated scenarios; this does not establish a game FPS gain.

Original plan:

- `JR $ra` sets `ctx->pc` and returns; the caller compares and continues. Keep it.
- `JALR` and `JR rX` (jump tables) go through `IndirectCall`: add a one-entry inline cache per call site
  (`static uint32_t lastPc; static Fn lastFn;`, filled from the table lookup; thread-safe because entries are
  immutable once registered).
- In `dispatchGuestBranch`, move the ring write and the getenv-static trace checks under one
  `if (unlikely(g_traceMask))` test, so the release path is one load and one branch.
- Delete the no-op `ps2TraceGuestWrite` hook in `include/ps2_runtime.h` (marked TODO) and its call sites in the
  write macros. It compiles to nothing, but it clutters every generated write and costs compile time.

### 1.3 Patch 30 `mem-fast-path`: cheaper guest memory access

**Blocked on evidence, not scheduled as a broad rewrite.** First add deterministic tests for every width
(8/16/32/64/128), unaligned access, RDRAM end crossing, segment mirrors, scratchpad, MMIO/DMA/timers and unmapped
addresses. `$sp`/`$gp` are conventions, not a proof of RDRAM residency: require range proof or a guarded fallback.
Do not remove a bounds check merely because a guard page exists; the actual PS2 aliasing/wrap behavior must match.
Only the classification fast path should be considered first. Mirrored virtual mappings are a separate experiment
with Windows allocation/granularity tests and a fallback on mapping failure. Keep the existing implementation
selectable for differential tests. Acceptance requires the P0/P1 gates above and measurable EE/frame-time benefit.


Today (`include/ps2_runtime_macros.h`, ~lines 470-640): `READ32/WRITE32` → `PS2Runtime::isSpecialAddress`
(`addr >= 32 MB` → out-of-line `Ps2IsSpecialAddress`) → `Ps2FastRead` (mask + contiguity check).

- Map kseg0/kseg1 mirrors (0x8000_0000 / 0xA000_0000 / 0x2000_0000 uncached) with the same mask, so they take the
  fast path instead of the out-of-line check.
- Reserve RDRAM with a guard page and a mirrored tail (map the first page again after the 32 MB end) so an access that
  straddles the end is still valid memory. This removes the contiguity check from 16/32/64/128-bit accesses.
- Where the recompiler can prove the base is `$sp` or `$gp` plus a small constant, emit the RDRAM access directly
  (no special-address test). The stack and small data are always RDRAM in GoW.

Risk: scratchpad (0x7000_0000) and hardware registers must keep their slow path; test with the existing register-
access traces. Measure with callgrind instruction counts on the EE.

### 1.5 Patch 32 / pipeline: faster, reproducible builds

**Brought forward into the foundation work.** Local cache installation, generation signatures, ownership-aware
sync, Clang-only orchestration and stage metrics are now implemented before patch 30. The bullets below describe
remaining tuning hypotheses; they are not measured speedups. In particular, hot/cold splitting does not yet establish
that compile time halves, and cache coverage must be measured with the actual PCH/PGO flags.


- **Compiler cache:** the runtime CMake already supports sccache (`PS2X_ENABLE_SCCACHE`, default ON) but the
  pipeline never installs it. Download it in the `fetch` stage (pinned version + SHA256, like Ninja). A rebuild after a
  runtime-only patch then recompiles only what changed. Note: sccache does not cache PGO-instrumented builds well;
  enable it for normal builds and for `-fprofile-instr-use` (profile file hash is part of the key).
- **Unity batch size:** CMake defaults to 32, `build.ps1` forces 8 (`-DPS2X_RUNNER_UNITY_BUILD_BATCH_SIZE=8`).
  Measure 8 / 16 / 32 with `ninja -j` on machine A (peak RAM vs wall time) and store the result as a profile value
  (`[build] unity_batch`), so a 16 GB machine can use 8 and a 64 GB machine 32.
- **Split by heat:** use the PGO profile to put cold generated functions in their own units compiled with `-O1`
  (`-Os`), and hot ones with `-O2 -march` level chosen per build. Measure compile time and runtime regressions before acceptance.
- **Configure signature** (`gow-configure.sig`, done in e2a0399) already skips configure; extend the same idea to
  the `recomp` stage: hash ELF + recompiler config + recompiler binary and skip when unchanged.
- **CPU target:** builds are generic x86-64. Offer `-march=x86-64-v3` (AVX2) as a launcher option with a CPUID check
  at start-up and a fallback exe. The VU1 JIT already picks AVX at run time; this helps the EE and GS code.

## Phase 2: performance, frame pacing, a locked 60 fps

### 2.1 Patch 33 `vu1-early-finish`: close the 3.5 ms serial gap

Already designed in the handoff doc (§ gap analysis): signal FINISH to the EE as soon as the last GS packet of the
frame is queued, with display-register writes ordered behind it, instead of after the VU1 job drains. Expected
+3.5 ms margin (55 → 60 in heavy areas). Risk: tearing or a one-frame-late display write; test with the GS dump
digest and on-screen.

### 2.2 Patch 34 `vu1-chain-lite`: cut `VU1NativeAccess::chain`

- ~130 instructions per block, half of block cost, in both JIT and AOT.
- Approach: precompute the successor for the common case (fall-through and unconditional branch) and patch a direct
  jump into the block's tail (JIT) / a direct call table index (AOT); only the conditional and indirect cases go
  through `chain`.
- The previous attempt gained ~2 % because it only skipped the lookup; the cost is mostly the timing / state
  bookkeeping. Profile which part of the 130 instructions is the timing table (`cyc`) and fold it into the block's
  static cycle count (this is phase 3 "VU1 static timing" of the handoff doc).

### 2.3 Patch 35 `vu1-selfloop`: self-loop fast path (handoff phase 5)

Blocks that branch back to themselves (vertex loops) run the loop inside one host function call with the cycle count
added per iteration; no `chain` per iteration.

### 2.4 Patch 36 `cd-read-cache`: remove disc read hitches

`ps2xRuntime/src/lib/Kernel/Stubs/Helpers/Support.h`:

- `readCdSectors` walks the whole `g_cdFilesByKey` `unordered_map` for every read (linear scan by LBN range).
- `readHostRange` opens a new `std::ifstream` for every read, seeks, reads, and `memset`s the buffer first.

On streaming areas (level loads behind gameplay) this is a source of frame-time spikes. Change: build a sorted vector
of `(baseLbn, endLbn, entry)` once and binary-search it; keep a small LRU of open file handles (or memory-map the disc
files); drop the `memset` when the read fills the buffer. The disc timing model (`CD.cpp`, field-clock sectors per
second) stays as it is, so load times on screen do not change; only host CPU cost does.

Measure: frame-time histogram (`GOW_PERF=1`) across a level transition; count spikes > 20 ms before/after.

### 2.5 Patch 37 `frame-pacing`: present on time

- `ps2_runtime.cpp:874` uses raylib `SetTargetFPS(gowVentanaFps())` (sleep-based) and VSync only with
  `TOBIICHI_VSYNC`. raylib's wait is coarse on Windows (timer resolution). Replace with a high-resolution waitable
  timer (`CreateWaitableTimerExW(..., CREATE_WAITABLE_TIMER_HIGH_RESOLUTION)`) plus a short spin for the last 0.5 ms.
- Pace to the guest's frame (`vid::Flip`), not to a free-running host clock: when the guest misses a frame, present the
  previous one at the right time instead of doubling the next. This is what makes "55 fps" feel like stutter.
- Expose in the launcher: VSync / pacing mode / FPS cap (exists) + a "frame time graph" overlay (F1 panel already has
  ImGui-like drawing).

### 2.6 GS backend on AMD

- Waffle's draw-batching commits saturate AMD's GL driver; keep them out or make batching size a setting.
- Fix the colour-tint bug in `gs/gpu/gs_hw_backend.cpp` (`tryShuffle` / CLUT path) before any visual feature; texture
  packs (phase 4) depend on correct CLUT decoding.
- Upload path: use persistent mapped buffers (`GL_MAP_PERSISTENT_BIT`) for vertex/texture streaming if the GL 4.4
  extension exists; fall back otherwise.

### 2.7 Threads

- IOP / sound engine on its own thread (it already has a transport, `ps2_iop_transport.h`); check how much EE time it
  takes today with `GOW_PERF`. If > 1 ms per frame, move it.
- Pin the VU1 worker and the EE thread to different physical cores (Xeon: avoid SMT siblings); a launcher option.

## Phase 3: audio

### 3.1 Patch 38 `cutscene-pcm-align`: PT-BR cutscene L/R blocks

From `docs/research/cutscene-audio-2026-10-26.md`: the PCM L/R 512-byte channel blocks are misaligned (256-sample
period, phase 164) at or before the SPU2 input mix in A01MP02. Next steps there: trace the demux in
`MPEG.cpp dispatchGuestStreamCallback / deliverPendingAudio`, then the EE→IOP chain at 0x188688 / 0x1884B0 /
0x188610, and log the byte offset at each hop until the phase appears. Fix at the first hop that shifts it. The
English edition is the control: same trace, phase 0.

### 3.2 Patch 39 `audio-rate-control`: no pitch drift

The resampler can consume up to 5 % faster than nominal to drain the queue, which raises pitch. Replace with a small
proportional controller on queue fill (±0.5 % max, the usual emulator range: inaudible) and a hard drop/insert only on
large underrun/overrun. Measure: a 1 kHz test tone through the mixer, frequency over 5 minutes.

### 3.3 Later

- Output latency setting in the launcher (buffer size), WASAPI exclusive as an option.
- Volume per channel group (music / SFX / voices) is possible because SPU2 voices are known; needs a voice → group map
  per game (profile data).

## Phase 4: ISO mods and texture packs

### 4.1 Pipeline: xdelta ISO patches (no runtime change)

- A `mods/` folder per game under `data/<id>/mods/*.xdelta` (or `.vcdiff`). The `discs` stage applies them in order
  to a copy of the ISO before extraction; the result's SHA1 goes into the build cache key.
- Launcher: a Mods page listing them with on/off; changing it marks the `discs` stage dirty.
- This covers existing community ISO mods (translations, rebalance) without code.

### 4.2 Patch 40 `vfs-mod-overlay`: loose-file mods

Hook point: `readCdSectors` / `CdFileEntry.hostPath` (`Kernel/Stubs/Helpers/Support.h`). When
`data/<id>/mods/files/<disc path>` exists, read from it instead. Constraint: the game reads by LBN and sector count
from its own TOC (`[disc] toc`), so a replacement must fit in the original file's sectors; larger files need the
xdelta path (4.1) to rebuild the TOC. Log a warning when an overlay is larger than its slot.

### 4.3 Patch 41 `pnach`: cheat / patch files

`gow_trucos.cpp` already writes guest memory for the F2 trainer. Add a PCSX2 `.pnach` reader (`patch=1,EE,addr,word,
value`) applied once per frame from `data/<id>/cheats/*.pnach`. Note: code patches (writes into the executable's
text) do nothing in a static recompile, because the code is already C++. Only data patches work; the reader must warn
on writes inside the ELF's text range (`[executable] text_sha1` gives the range).

### 4.4 Patch 42-43 `texture-dump` / `texture-replace`

Hook point: `gs/gpu/gs_texture_store.cpp` (`DecodeTextureRgba`, `LoadClut`, `ClutHash`).

- Dump: hash = (TEX0 address/format/size + data hash + CLUT hash), PNG written once per hash to
  `data/<id>/textures/dump/`. Use the PCSX2 hash and naming where possible, so existing PCSX2 packs map (PCSX2
  replacement uses `<TEX0 hash>-<CLUT hash>-<format>.png`).
- Replace: load `data/<id>/textures/replace/*.png` (and `.dds` with BC7) into a hash map at start; on decode, upload
  the replacement at its own resolution and scale UVs. Async loading on a worker thread; first use may show the
  original for a frame.
- Depends on 2.6 (CLUT tint fix), otherwise hashes of paletted textures are wrong.

## Phase 5: upscaling, sharpening, "DLSS"

What exists: `gs/gs_host_present.cpp` has a Catmull-Rom bicubic scaler + contrast-adaptive sharpen + FXAA
(`GOW_SCALER`, `TOBIICHI_FXAA`). The GS renders at native 512×448; Hor+ widescreen exists, HUD is stretched.

### 5.1 Patch 44 `gs-render-scale`: internal resolution

The real quality jump: render the GS target at 2×/3×/4× (scale vertex XY, scissor, and the frame/depth buffers) in
`gs_hw_backend.cpp`. This is what PCSX2's upscaling does. Hard parts: VRAM readbacks (EE reads of the frame buffer)
and offset bugs (half-pixel); a per-game "native readback" fix list. Highest visual value, medium-high risk.

### 5.2 Patch 45 `present-fsr1`: AMD FSR 1 (EASU + RCAS)

Spatial only, open source (MIT), GLSL ports exist. Replace the bicubic pass with EASU at the window resolution and
RCAS for sharpening; keep bicubic as the fallback. Works on every GPU. Cheap: one extra pass.

### 5.3 Patch 46 `present-dxgi`: a DirectX presentation layer

Why: NVIDIA Smooth Motion / driver frame generation, AMD Fluid Motion Frames (AFMF), OptiScaler, ReShade (best on
DX), RTSS frame limiting and Windows Auto HDR all hook DX11/DX12/Vulkan swapchains, not OpenGL.

Approach: keep GL rendering; share the final image with a D3D11 swapchain through `WGL_NV_DX_interop2` (works on
NVIDIA, AMD and Intel on Windows), present with `IDXGISwapChain` flip model (`DXGI_SWAP_EFFECT_FLIP_DISCARD`,
waitable object for pacing, tearing support for VRR). Fall back to GL present when interop is missing.

This alone enables driver frame generation (AFMF / Smooth Motion): 60 → 120 on screen without engine data.

### 5.4 DLSS / FSR 2-3 / XeSS (temporal upscalers): what is possible

- They need per-pixel motion vectors, depth and jitter. A PS2 game produces none of these; the GS gets
  already-transformed screen vertices.
- Partial route: VU1 output holds per-vertex screen positions per frame; matching draws across two frames (same
  texture/state hash and vertex count) gives motion per vertex, rasterised into a motion buffer. Works for skinned
  characters and static geometry; breaks on particles and UI. It is a research project (weeks), not a patch. Do 5.1
  and 5.3 first; with 5.3, OptiScaler can at least inject FSR 3 frame generation / XeSS using its own heuristics.
- Recommendation: 5.1 (render scale) + 5.2 (FSR1) give most of the visual gain; 5.3 gives frame generation.

### 5.5 HUD in widescreen

Detect HUD draws (2D sprites with no Z, drawn after the 3D pass, by texture hash list in the profile) and scale them
back to 4:3 centred. Data-driven: the hash list is per game (`games/<id>/game.toml` `[widescreen] hud_textures`).

## Phase 6: the GoW2 hook

Today: `games/gow2/game.toml` is `status = "planned"` with empty fields; `docs/adding-a-game.md` lists steps 1-8.

What blocks a second game in the code:

1. **Game code in the runtime patches.** `gow_trucos.cpp`, `gow_integracion.cpp`, `gow_fijar.cpp`,
   `gow_cancelar.cpp`, `gow_sondeo.cpp`, `gow_espera.cpp`, `gow_video.cpp` hold 114 hard-coded GoW1 guest addresses.
   They must only register when the ELF matches GoW1 (`game_overrides.cpp` already matches descriptors by ELF name and
   CRC). Patch 47 `game-gate`: wrap each module's registration in the descriptor of its game; nothing runs for
   another ELF. Later move the addresses into a per-game table (`games/<id>/addresses.toml` → generated header).
2. **Global patch list.** `fetch` applies every `engine/patches/*.patch`. Add `[runtime] patches_exclude = [...]` (and
   an optional `patches_extra` dir under `games/<id>/patches/`) to the profile, so game-specific fixes live with the
   game. Engine-wide patches stay in `engine/patches/`.
3. **Per-game constants in the pipeline.** `frame_pc`, the PGO pad script, VU1 microcode capture (`vu1disc`),
   language hints: already profile values. Check `build.ps1` and `profile.py` for any remaining literal `gow1` /
   `SCUS_973.99` and replace with profile reads.
4. **Function map for GoW2.** Run the analyzer on SCUS_974.81 (same engine generation as GoW1, so most overrides
   — `vid::Flip` equivalents, pad, sound RPC — should be found by signature). Write a signature matcher script that
   takes GoW1's override list and finds the same functions in GoW2 by byte pattern (masked relocations).
5. **VU1 microcode.** GoW2's renderer microcode differs; the `vu1disc` stage (ISO microcode extractor) and the JIT
   handle unknown programs at run time, so GoW2 can boot on the JIT before any AOT VU1 module exists.

Order: 47 (gate) → profile fields → analyzer + signature matcher → first boot on interpreter/JIT → overrides.

## Rules for whoever implements these

- One patch per item, applied on top of 01-27 in `engine/patches/`; regenerate with the chain script, never edit the
  runtime checkout in place. Update `engine/README.md` (table row) and `AGENTS.md` if a contract changes.
- Never commit game data: ISO, ELF, recompiled C++, VU1 captures, `disc_*.bin`, PGO profiles, analysis cache,
  `gow-native.boot`, saves, dumped textures. All of it lives under `data/`.
- Every performance claim needs the same measurement before and after (`GOW_PERF=1` on the ship and A01MP02, or
  instruction counts), written into this file's item.
- Every codegen change passes the GS-digest differential run (1.7) before it ships.
