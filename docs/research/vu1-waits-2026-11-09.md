## CPU versus waiting

The existing Windows sampler now supports `SAMPLER_CPU_ONLY=1`. It opens threads
with query-only rights, reads GetThreadTimes, discovers new threads every 250 ms,
and never suspends threads, initializes symbols or changes timer resolution.
CPU time is separate from the interval for which each thread was observed;
unused time cannot be split into sleeping versus runnable scheduling delay by
this counter alone. Retired threads are not a continuous-worker measurement.
The integration fixture keeps one busy and one sleeping thread alive throughout:
three seconds yielded 3000 ms / 0 ms CPU, with zero instruction samples.

Run `load-cost` enabled scoped timing, VU/GS cost counters and a bounded task
capture (32 records, stride 256, delay 40 s). Counter-only measurement was
approximately collector seconds 45–65. The VU worker (thread 7804, consistent
with the cost trace) used 19984.375 ms CPU over 20035.044 ms: **99.75% of one
logical core**. The trace around 50–65 s attributes approximately 4.56 s/5 s to
VU execution; estimated chain cost was 2.63–2.68 s per reporting interval.
Those sampled/nested cost estimates are intrusive wall times, not additive CPU
self-time percentages. `finish_ms` includes more than finishBlockTiming alone.

Queue 1 is the producer's GS-stage ring. After the initial capture disturbance,
its final 36.318-second window recorded only 1.956 ms of capacity waits (maximum
1.346 ms). Queue 2 recorded roughly 202–231 ms per five seconds in later windows;
that is the stage/backend queue, not evidence that the VU thread slept for that
time. These counters include their timed active waiting and must not be added
to CPU-time totals. They do not explain multi-second VU cost in this workload.

Run `load-clean` removed detailed timing, task capture and VU/GS cost probes;
only basic frame/audio metrics and player trace remained. Counter-only sampling
again covered approximately 45–65 s. The subsequently identified VU worker,
thread 7632, consumed 19718.750 / 20103.557 ms: **98.09% of one core**.
A separate four-second instruction sample after that interval resolved against
the exact installed executable's COFF symbols: `VU1NativeAccess::chain` accounts
for approximately **33.8% of its wall instruction samples**. A native block
`b0d00_53ba0530` accounts for 5.46%, GS-stage push 2.99%, scalar timing 2.21%,
blockTiming 1.43%. The table is not a CPU self-time profile. Suspending threads
reduced the observed VU CPU fraction during instruction sampling, so sampled
periods are excluded from all FPS observations below.

Conclusion for this scene: the VU worker is predominantly executing, with small
measured capacity waits, rather than spending most of its wall time blocked.
Chain/bookkeeping is the largest identified hotspot. This does not prove every
slow area has the same bottleneck, nor justify removing synchronization, flags,
scalar timing or arithmetic correctness. VU-01..08 already reject several such
chain/layout/branch candidates; none was silently reintroduced.

## Correction: patch zzz-315

`recordTask` checked delay, stride, recording failure and exhausted limit inside
a no-inline lambda containing a complete temporary interpreter. With capture
configured, it entered/probed that large stack frame on every VU program,
including after the capture limit. This is the diagnostic variant of GAIN-07's
large-frame issue: the disabled-recording path was already guarded correctly.

Move the existing mutex and selection gates before entering the cold lambda.
State stays protected through the entire write, selected records retain the
same order/contents, and no new lock-free read or changed execution semantics
is introduced. The normal recording-disabled path is unchanged. This corrects
research overhead; it is not a normal gameplay performance patch.

A bounded fixture now accepts 1–1,000,000 executions. Three alternating pairs,
pinned to one available logical CPU, each execute one million synthetic programs
with the capture limit at three. Reference times: 0.762924 / 0.729317 / 0.730440 s;
candidate: 0.652857 / 0.648603 / 0.636104 s. Median 0.730440 → 0.648603 s,
**11.20% lower elapsed time for this diagnostic fixture**. All six final digests
and captured corpus hashes match. These short process-wall times include startup;
they are not per-call cycles, gameplay FPS or an estimate of normal-play gain.

An initial attempted fixture reference/candidate pair had identical binary
hashes because Copy-Item preserved source modification times and Ninja did not
recompile. It was rejected before timing. Both sources were then explicitly
marked modified, core rebuilds confirmed and different executable hashes
recorded. The invalid build logs/binaries remain in the evidence directory.
