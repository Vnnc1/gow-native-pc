# fix-chore on an i3-10110U / Intel UHD notebook (2026-11-07)

First measurements of the integrated fix-chore chain (PR 26 + fix-chore, 115 patches) on a 2-core notebook, the
renderer and harness defects they exposed, and the new patches zzz-302..304. Evidence (game-derived, never packaged)
is under the measuring copy's ignored `data/perf-i3-10110u/`.

## Machine and method

- Intel Core i3-10110U (2C/4T, 15 W), 12 GB, Intel UHD Graphics, driver 26.20.100.7870, Windows 10 Pro 19045.
- AC power (battery charging), power plan "Atlas Power Scheme" chosen by the owner and kept for every run.
  Thermal zone 60 C at idle after the runs. The CPU throttles: the per-frame cost of *every* thread rose by up to 2x
  between consecutive pairs (EE and VU1 together), so absolute FPS across sessions is not comparable.
- Prepared PT-BR disc, the installed copy's recorded VU1/IOP code (native coverage complete: `missBlocks=0`),
  private blank cards, audio on, visible 1280x720, 1x internal, no PGO (small-CPU install path).
- Runners (SHA-256): v0.5.0 install `addbb549...95fa3`; fix-chore + zzz-302 `6e9d62dd...30767`; + zzz-303
  `d86d7751...14613`; + zzz-304 `3278b594...bcabf`.
- Because of the throttling, decisions use **within-pair** comparisons and, for CPU work, the **per-guest-frame thread
  cost** in windows where VU1 is >= 60 % busy ("heavy"), from `[gow-perf]` in `--timing` sessions. That ratio does not
  depend on how long a run spent in a light scene; real-time input makes scene progress differ between runs.

## Where the time goes

`GOW_VU1_COST=1 GOW_GS_COST=1` (session 06): in heavy windows the VU1 worker is busy ~4.65-4.69 s of every 5 s.

| Part of the VU1 worker | ms per 5 s | Note |
|---|---:|---|
| `VU1NativeAccess::chain` (block-to-block bookkeeping) | 1840-2642 | 40-58 % of block time, 60-93 ns per call, ~6 M calls/s; `finishBlockTiming` about half of it |
| XGKICK -> GS frontend (`submit`) | 711-838 | 155-168 ns per vertex, 600-730 k vertices/s |
| Generated block arithmetic | ~1200 | the rest of block time |
| Producer waits for the render worker | 73-128 | small |

VU1 costs 26-36 ms per heavy guest frame (60 FPS needs <= 16.7), EE 11-15 ms, GS 10-14 ms. The GPU is not the limit
here (busiest engine 49-75 % mean with `--gpu-samples`). Native VU1 coverage is complete, so this is the cost of the
AOT code and of `chain`, not of JIT/interpreter fallbacks. `NativeState::slots` is 2048 x 128 B = 256 KB, the size of
this CPU's per-core L2.

## Results

### v0.5.0 vs fix-chore + zzz-302..304 (FPS sessions, 3 pairs, `worker-ab.py --experiment build`)

| Pair | v0.5.0 guest FPS / median window p95 | fix-chore |
|---|---|---|
| 1 | 51.96 / 17.3 ms | 41.44 / 37.7 ms |
| 2 | 42.51 / 31.2 ms | 42.47 / 35.3 ms |
| 3 | 43.64 / 31.8 ms | 42.76 / 34.4 ms |

Window by window, the heavy ship section ran ~23-26 then 36-39 FPS on v0.5.0 and ~19-22 then 29-35 on fix-chore in all
three pairs; p95 was worse for fix-chore in 3/3. A timing pair (session 05) put VU1 at 24.6 vs 26.6 ms per heavy frame
(+8 % for fix-chore) in pair 1; pair 2 was throttled in both variants (38-42 ms) and favoured fix-chore. **Decision:
fix-chore is not faster than v0.5.0 on this machine; the heavy section is likely slower. Cause not isolated** (see
open items).

### PR 26 renderer set (`gs-run-ab.py --compare pr26`, 3 pairs, FPS + GPU samples)

Off (every PR switch and grouping off) 41.68 / 35.97 / 43.21 vs on 38.77 / 40.02 / 28.08 guest FPS. Off won 2/3. The
28.08 run stayed ~20 FPS for its last 25 s (288 frames > 50 ms) and one "on" run lost 5,187 audio frames, but runs
also reached different scenes (two "off" runs reached the light 60 FPS phase, the "on" runs mostly did not), so this is
**no demonstrated benefit and no proven regression**. The renderer work runs on a GPU that is not the bottleneck here.

### Same-binary switches (timing, 3 pairs, VU1 ms per heavy frame, variant 0 vs 1)

| Switch | Pair 1 | Pair 2 | Pair 3 | Decision |
|---|---|---|---|---|
| `GOW_VU1_CHAIN_WARM` (patch 76, default on) | 35.48 vs 32.41 | 34.03 vs 36.49 | 32.64 vs 33.24 | neutral; default kept |
| `GOW_VU1_FAST` (patch 51, launcher option) | 33.75 vs 33.93 | 33.88 vs 31.77 | 41.63* vs 31.81 | at most ~6 %; float semantics change; stays opt-in |

\* the variant-0 run of pair 3 throttled (20 FPS, 117,079 missing audio frames); not a valid pair.

Audio starves under sustained VU1 saturation: 1,000-12,000 missing frames per 130-150 s session were common in the
later, hotter pairs, in both variants of every switch.

### zzz-302 / zzz-304 wrapping-blend grouping

Every COLCLAMP=0 shader-blend batch of the route was 4 triangles (two quads), ~1,200-1,700 batches per 5 s. zzz-302
alone grouped nothing (`draws == tris`: the bounding boxes of a quad's halves always meet). With zzz-304's exact
shared-edge / separating-line test, `[gs-hw-wrap]` shows draws = tris / 2 (e.g. 6,912 tris -> 3,456 draws), i.e. per
batch 2 draws and 1 barrier instead of 4 and 3. FPS is unchanged within noise on this CPU-bound machine (one timing
pair 42.83 vs 44.28). Expected to matter where the GPU is the limit; retained because the result is exactly that of one
draw per triangle (GL rasterization rules) and `GOW_GS_WRAP_GROUP=0` restores the old path.

## Defects found and fixed

- **Harness blind since the PR 26 integration.** `gs-run-ab.py` requires `[gs-run-config] enabled=N`, which the PR's
  `GS::GS()` no longer printed, so every session failed `effective_setting`; and `queue_healthy` searched for
  `[gs-run] queue record issue:` while the runtime prints `[gs-run] dropped a queue record:`, so that check always
  passed. zzz-303 prints the marker again (and `[gs-wrap-config] group=N`); the harness checks the real message.
- **Harness forced PR switches off.** Non-PR modes set `GOW_GS_HW_RING=0 GOW_GS_TEXREUSE=0`, so they did not measure the
  shipped renderer. New `SHIPPED_FLAGS` modes (`wrap-group`, `chain-warm`) keep the PR set and grouping at their shipped
  values; `--env NAME=VALUE` passes diagnostics/overrides to both variants.
- **`patches.ps1 start -Onto` stopped after the first pick** on machines without a git identity: the identity it sets
  for the generated commits was restored before the rebase, which also commits. The rebase now gets the same technical
  committer; `patch-stack-tests.ps1` passes.
- The per-triangle wrap-blend path existed unchanged in fix-chore (`gs_hw_backend.cpp`), with no counter: fixed above.

## Not changed, recorded

- `vu1n::macBits` (PR) also sets the overflow bit when a result equals the largest float (saturated), not only for
  Inf/NaN exponents. Exactness change, not performance; not reviewed against hardware here.

## Future work (hooks left on purpose)

Deferred at the owner's request on 2026-11-07 so that the release setup could be produced the same day. Each item says
what to run and what decides it; record results here, in the ledger and in `docs/tested-hardware.md`.

1. **PGO gain on this machine.** A `pgo` run on this chain (118 patches) finished its training (profile SHA-256
   `84b50eb6...59f24672`, manifest `source: trained`, 2026-11-07T22:24Z) and was then **cancelled by the owner** during
   the ~30-40 min final build. The profile is kept, unused, in the measuring copy's ignored
   `data/gow1/pgo-trained-20261107/`; the installed game was rebuilt without PGO and the setup still ships none. To
   use it: move both files back to `data/gow1/pgo/`, run `build.cmd -Stages configure,build` then `-Stages pgo-check`;
   for a release, copy them to the packaging checkout's `data/gow1/pgo/` and build `installer` without
   `-NoReleaseProfile` (any later runtime/patch/game-profile change invalidates the manifest; retrain then). Then run `gs-run-ab.py --compare vu1 --reference-runner <non-PGO runner> --runner <PGO runner> --timing --pairs 3`
   (both runners kept under the measuring copy's `data/candidate-*`), and judge VU1/EE ms per heavy frame within pairs
   (`perframe`-style analysis of `[gow-perf]`, see "Method"). Earlier evidence: GAIN-09 (+4.7 % FPS, Xeon/RX 580).
2. **v0.5.0 -> fix-chore regression (heavy section ~10-15 %).** Capture one corpus (`gs-run-ab.py --task-capture`),
   build `gow_vu1_tasks` for both runtimes (v0.5.0 = backed-up 01-61 chain; fix-chore = current chain) and compare with
   `tools/test/vu1-task-ab.py`. If VU1 replay ties, the difference is outside the VU1 interpreter: compare the XGKICK
   frontend (`GOW_GS_COST=1` `[gs-fe] per_vertex_ns`; v0.5.0 has no counter, so time `submitGifPacket` with a sampler,
   `tools/profile/sampler.cpp`). Do not change defaults until the cause is named.
3. **`chain` bookkeeping** (40-58 % of VU1 block time, 60-93 ns/call, ~6 M calls/s). Profile with the sampler before
   proposing a change; VU-01/04/05/06/08 list chain variants that already failed, do not repeat them under new names.
4. **Audio starvation under sustained VU1 saturation** (1,000-12,000 missing frames per session in hot pairs). Correlate
   `GOW_AUDIO_STATS` with the VU1-busy windows; no blanket buffer increase as a substitute for a cause (P1 in the
   [checkpoint](render-delivery-2026-11-04/resume-checkpoint.md)).
5. **zzz-304 on GPU-bound hardware** (weak GPU, strong CPU; e.g. HD 4400 or the RX 5500 XT Hydra scene of GPU-01):
   `gs-run-ab.py --compare wrap-group --gpu-samples --pairs 3`, plus a captured-frame comparison of both variants.
6. **`vu1n::macBits` overflow-on-saturation** (PR change): check against the exact interpreter and real-hardware VU
   semantics before relying on it.
7. **Thermal method.** This notebook throttles within ~30 minutes of sessions; future A/B on it should alternate more
   pairs with cool-down pauses, or record clocks, before reading single-digit percentages.
